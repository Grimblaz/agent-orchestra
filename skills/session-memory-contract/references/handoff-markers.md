# Cross-tool Handoff Markers

Durable GitHub comment markers used by Agent Orchestra for phase handoffs, smart resume, engagement records, and credit ledger. Markers are HTML comments written to GitHub issue or PR threads; because they live on the issue, work resumes across sessions without losing context.

Row-level survival and fallback semantics: [../SKILL.md](../SKILL.md) (session-memory-contract).  
Persistence rationale: [../../../Documents/Design/session-memory-contract.md](../../../Documents/Design/session-memory-contract.md).

- `goal-run-inflight-{Issue}` — durable issue-comment mutex marker for a live `/goal-run {issue}` launch attempt (issue #874, plan step 4, M8; adoption primitive and additional resolution sites added in #912 step 4). Payload is a Markdown bullet list (schema_version, issue, status, contract_hash, launched_at, an optional resolved_reason once withdrawn, and an optional adopted_by_session_id once adopted), never a fenced YAML block. `status` is a three-value enum: `unresolved | resolved | adopted` — `adopted` is a distinct value from `resolved`, so a body read can tell "adopted, run in progress under a new session" apart from "resolved, marker withdrawn/completed". **Writer**: `New-GoalRunInflightMarker` (`.github/scripts/lib/goal-run-stage-core.ps1`), which always POSTs a fresh comment (never upserts) — launch order is marker-first, then provision: the marker is posted BEFORE `New-GoalRunWorktree` is ever called, and a post failure aborts the launch with no worktree created. After posting, `Invoke-GoalRunMutexLaunch` re-fetches every live marker for the issue and tiebreaks via `Resolve-GoalRunInflightMutexOutcome`. **Live means `status: unresolved` OR `status: adopted`** — an adopted marker is a run still in progress under a different session, not a withdrawn one, so excluding it would let a second invocation see an in-progress run as absent and provision a duplicate worktree. The tiebreak outcome: the lowest (earliest) comment id proceeds to provisioning, every other live marker yields and is patched to `status: resolved` via `Set-GoalRunInflightMarkerResolved`. Mutex-yield is no longer the only resolution site: `Resolve-GoalRunInflightMarkerForResolution` (same file) re-fetches and identifies the winning live marker — the same `unresolved`-or-`adopted` liveness test the mutex reconcile applies, so a marker this session itself just adopted stays findable when that session later resolves it — for every other halt or completion point in the `/goal-run` stage machine — the pre-loop launch-pin halt, every chain-stage-boundary halt, the Stage 1 fix-cycle-cap halt, the `loop-interrupted` guard/re-validation halts, and Stage 5's `run-complete` completion path (`agents/Goal-Run.agent.md`) — each of which then calls `Set-GoalRunInflightMarkerResolved` with a reason naming that specific site. A held marker can also transition to `adopted` instead of `resolved`: `Set-GoalRunInflightMarkerAdopted` PATCHes the marker to `status: adopted` plus the adopting session's id, then re-fetches and verifies the mutation actually landed (`Reason` one of `adopted-and-verified | already-adopted | already-resolved | marker-status-unrecognized | patch-failed | verification-comment-not-found | verification-body-unchanged | verification-status-mismatch | reconfirm-comment-not-found | lost-to-concurrent-adopter`) — this is the mutation `Resolve-GoalRunInvocationAction`'s `adopt-and-resume` action performs before a dead-appearing or explicitly force-adopted run resumes. **When the adoption pre-check's own re-read succeeds**, the adoption admits only a freshly-read `unresolved` status: a marker the owning run already resolved refuses as `already-resolved`, and one whose status line is missing or unrecognized refuses as `marker-status-unrecognized`, rather than being PATCHed back to `adopted`. That qualifier is load-bearing and the guarantee does not extend past it: the pre-check gate is nested inside a successful comment read, and `Get-GoalRunIssueComments` is fail-open (`@()` on any transport or parse failure), so a transient `gh` failure skips the gate entirely and the PATCH lands on a marker whose live status was never observed — including a `resolved` one, whose `resolved_reason` it then destroys. The function still reports `Verified: $false` (`verification-comment-not-found`) in that case, so a caller that stops on `Verified: $false` is safe, but the mutation has already happened. Do not read this row as license to skip a caller-side guard. Tracked by [#928](https://github.com/Grimblaz/agent-orchestra/issues/928). **Reader**: `Get-GoalRunInflightMarkers` (mutex reconcile) and `Test-GoalRunInflightAppearsDead` (crash-atomicity: a marker with no recent heartbeat is a first-class detectable "appears dead" state that `/goal-run {issue}` reports instead of silently launching a duplicate run). On `status`, that deadness check short-circuits on `resolved` ONLY — an `adopted` marker falls through to the same purely elapsed-time staleness computation an `unresolved` one gets, because an adopted run can crash just like any other. One non-status short-circuit also precedes the elapsed-time computation: a heartbeat that is present but unparseable returns `AppearsDead: $false` / `heartbeat-unparseable-assumed-live` regardless of status, failing closed rather than casting. Whether a terminal outcome (halt report or PR) exists never suppresses the staleness verdict; it is surfaced separately as `TerminalOutcomePresent` so the invocation-action precedence can compose "stale" and "terminal outcome present" as two independent signals. **Survival semantics**: `durable` (GitHub issue comment on the subject issue); this row now supersedes the prior "reserved, zero matches" registration from #874 plan step 1.

## What the write-path rule buys — and the hazard it does not reach

**Read this before replacing any comment's whole body.** This is the single home for the *full* hazard prose — the reader census, the acceptance, and the revocation condition live here and nowhere else. Surfaces in the entry-point set carry a one-line statement of what the rule buys and point here for the rest; other statements of the rule in this repository are deliberately left unqualified, and are enumerated in the `3.18.0` CHANGELOG entry. Do not read this section as a claim that every statement of the rule is qualified.

**The rule above is keyed on who composes the call, and that key does not track the hazard.** What the rule buys is a **single audited writer** — one place where the family registry, payload hygiene, validator adapters, burst ordering and idempotency are enforced. That is a real and separate good, and it is the whole of what the rule delivers. It is **not** protection from `updated_at` advancement, because the sanctioned primitive performs the very same whole-body replacement a hand-composed call would.

**Which writes actually replace a whole body — this is a property of the write *shape*, not of the primitive.** Getting this wrong in either direction is easy, so the split is stated rather than implied:

| Write | Families | What it does to a co-located family |
| --- | --- | --- |
| **`upsert`** — replaces the target comment's whole body | `plan-issue`, `frame-slices`, `completion-account`, `phase-containment-ledger`, `frame-credit-ledger` | **Advances `updated_at` on every family sharing that comment.** `Set-CommentBodyDirect` (`.github/scripts/lib/marker-transport-core.ps1`) issues a raw PATCH by comment id. `persist-phase-ledger.ps1` reaches the same function through `Set-PPLCommentBodyDirect`, including in `-Mode design`, whose "append" is a read-modify-rewrite rather than an append API. `frame-credit-ledger.ps1` reaches the identical whole-body-PATCH shape by a different route — `Find-OrUpsertComment`'s own `gh api -X PATCH`. Both `phase-containment-ledger` and `frame-credit-ledger` are live writers outside the `persist-marker.ps1` registry (they are `$script:MarkerHygieneOnlyFamilies` rows, tracked for cross-family hygiene but not for write dispatch); this table is not scoped to the registry, and neither should any reader scanning it for their own family assume that a registry absence means a post-new write. |
| **`post-new`** — POSTs a fresh comment | `design-phase-complete`, `experience-owner-complete`, `review-judge-produced`, `engagement-record`, `review-dispositions`, `credit-input`, `open-for-work-affirmed` | **Advances nothing.** A new comment has no co-located families. The primary write never reaches `Set-CommentBodyDirect`; these rows carry no PATCHing post-step. One narrow exception, on the comment the call itself just created: the create path's read-back-failure repair PATCH, which is what voids a fresh `open-for-work-affirmed` record as an ordering witness — see the recovery note in `skills/open-for-work/SKILL.md` § Writing the affirmation record. Nothing else PATCHes a `post-new` write's own output; a *different* write later replacing a body this record shares is a foreign write, not an exception to this row. |
| **post-step splice** | `frame-slices` post-step, on the `plan-issue` comment | **Advances `updated_at` on the plan comment**, which is an `upsert` family. This is the write `agents/Issue-Planner.agent.md` § Frame-slices sibling names as script-owned. A second, unrelated post-step splice exists: `persist-phase-ledger.ps1`'s `Resolve-PPLLedgerSibling` PATCHes the **plan comment** (a foreign family's comment, not its own) to insert the `phase-containment-ledger-ref` pointer — the same consequence, on a different target, from a different family's writer. |

So the hazard reaches you when you replace a **whole body** — your own family's or, far worse, one you do not own. It does not reach you merely because you wrote through the primitive.

**A whole-body write can do worse than advance a timestamp — it can delete a foreign family's content outright**, and that is a distinct consequence from everything above, on a different axis. `Invoke-MarkerUpsertWrite` composes the candidate and hands it straight to `Set-CommentBodyDirect`; there is no per-family merge. If the caller's candidate does not carry forward a foreign family's content, the PATCH erases it — not touches its clock, destroys it.

In practice this cannot happen through the sanctioned primitive for any of the twelve marker families it recognizes (the ten in the registry, plus `frame-credit-ledger` and `phase-containment-ledger`): payload hygiene refuses any candidate that carries a second registered family's marker at line start, so a caller can neither *drop* nor *accidentally recreate* the collision — the same rule that would make preservation impossible also makes the co-location unreachable in the first place. That is why the base rate for this failure mode is **structurally zero, not merely unobserved**: no comment in this repository's corpus has ever carried two of the twelve at line start, and the write path cannot produce one. Families outside that set (an unregistered marker literal quoted in prose, or ad hoc content a caller composed by hand) are not protected by hygiene and can genuinely be lost on a re-persist; `agents/Issue-Planner.agent.md`'s `plan-issue-write-back-preserve` post-step exists precisely to carry forward the specific cross-writer artifacts on that comment that would otherwise be silently dropped.

`updated_at` never moves backwards, and the GitHub API offers no `If-Match` or `ETag`, so a whole-body write cannot be made conditional. Once a family's timestamp is advanced there is no repair: a second write advances it again.

### The hazard is accepted, deliberately — and here is what would revoke it

**This is a recorded decision, not an oversight, and not a gap nobody looked at.** [Issue #1011](https://github.com/Grimblaz/agent-orchestra/issues/1011) put the question — what governs a whole-body comment write when the comment carries families it does not own — through design, and concluded a **reasoned acceptance**.

**The evidence it rests on:**

- **The base rate is zero.** Re-derived **2026-08-09**: **18 records across 11 issues** — 16 registered-form across 9 issues, plus 2 in the interim practiced form on 2 further issues — of which **17 are lawful** and **1 is void**. That one, comment 5162735720 on #990, is a self-declared test fixture: its own body reads "Edited after creation, deliberately, to exercise property 4." **Observed occurrences of a repair-PATCH voiding a real record: zero.** Read the two population figures together: 9 is the *registered-form* issue count and pairs with 16, not with 18. The corpus is live and grows legitimately, so treat these as of that date, not as constants; what matters is that the void count stayed at one while the denominator grew.

  Re-derive it with the lookup in `skills/open-for-work/SKILL.md` § Resuming an issue already opened for work: read each candidate issue with `gh api repos/{owner}/{repo}/issues/{ID}/comments --paginate`, keep only comments whose **first line** is the registered marker or the interim practiced form's exact literal, and compare `created_at` against `updated_at`. The first-line test is what produces the count.

  **Characterize the candidate generator honestly, because it is the weakest link.** Candidates come from `gh search issues --repo {owner}/{repo} --match comments "open-for-work-affirmed"`. That is **not** a substring match over comment bodies — it is a tokenized index query, and its recall is uncharacterized in *both* directions. It over-generates (issues that merely mention the family come back, which the first-line test discards). **Whether it can under-generate is unverified in either direction**: an issue whose only record is in the interim practiced form contains the string `open-for-work-affirmed` nowhere at all, which would suggest it is unreachable — but the search is a tokenized index query, not a substring match, and has in practice returned such an issue anyway (`gh search issues --match comments` returned #977 despite the literal appearing zero times in its body or comments, reproduced across repeated runs). Do not rely on that as a guarantee: the mechanism by which the index found it is not characterized here, and a future record could still be missed. Both interim-form issues in the figures above were confirmed present in the generator's output. The index also lags and the search carries a default result limit. Treat any denominator derived this way as a **floor**, and say so when you report one.
- **The mechanism candidates failed on evidence, not on cost.** A family-keyed guard at the transport chokepoint is not expressible — `Set-CommentBodyDirect` takes Owner/Repo/CommentId/NewBody and no `Family`, and no caller passes one. "Edit-sensitive artifacts always get their own comment" is false in-tree, and following it would disable the `863-D4` co-location counting gate.
- **This repository adopts mechanisms on ledger evidence, never on argument** (`Documents/Design/phase-containment-ledger.md`). There is no ledger evidence here yet.

**Two inherited figures are expressly retired here, so nobody re-inherits them.** Both come from issue #1011 and neither reproduces.

- **"The rule is stated 21 times across 13 files."** Retired. No phrasing reproduces it at #1011's own named commit `b4e8991`. The nearest candidates there: the case-sensitive literal `ONLY documented write path` gives 28 hits across 16 files; a markup-tolerant four-phrasing sweep gives 28/18 case-sensitive and 42/22 case-insensitive. What population 21/13 named is unknown. Treat any count of this rule as a floor, and state the exact command that produced it.
- **"Live census at `b4e8991`: thirteen registered-form records across eleven issues."** Retired as an **error**, not as staleness. Registered-form records have only ever spanned **9** issues, and issue coverage only ever grows, so `(13 records, 11 issues)` is unsatisfiable at every point in the corpus's history — the 11-issue threshold is never reached, and by the time even 10 issues could be, the corpus already holds more than 13 records. The deeper defect is the attribution itself: **a tree commit cannot pin a live-comment corpus.** `b4e8991` constrains nothing about what comments existed. Date a corpus census, never a SHA — which is why the figures above carry `2026-08-09` and not a commit.

**What revokes it:** a single observed occurrence of a whole-body write damaging a family it does not own, recorded in `Documents/Design/phase-containment-ledger.md`. The #944 corpus repair is the zeroth such record — it advanced timestamps, but on those artifacts the affected check was **unreachable**, so nothing was damaged.

**Nothing accrues that record automatically — say so rather than letting the naming pass for the accruing.** The ledger's narrative sections are hand-authored; `persist-phase-ledger.ps1` writes finding blocks, not incident prose, and no writer anywhere emits "a whole-body write damaged a foreign family". The one detector that fires at all is `repair-phase-containment-regions.ps1`'s pre-write co-location disclosure (`Get-CoLocatedMarkerFamily`), and it prints to the console, so it is gone when the run ends. The accrual path is therefore a **person**: someone sees the disclosure or the damage and writes the ledger entry by hand. If you are that person, this is the moment.

**If you are reading this from a consumer repository, that path is dead as written.** This file ships in the plugin, but `Documents/Design/phase-containment-ledger.md` is repository-local to agent-orchestra and does not exist at your repo root — the only copy is read-only inside the plugin cache. File the observation upstream as an issue on `Grimblaz/agent-orchestra` instead, naming the comment id, the family whose `updated_at` moved, and the write that moved it. An observation nobody can record is an acceptance nothing can revoke.

### This qualification carries no automated defense — keep it deliberately

The paragraphs above have **no test**. That is a decision on #1011 — an acceptance is not a behavior — rather than an oversight, and it is recorded here because the alternative is worse than silence: the suite pressures the other way. `.github/scripts/Tests/named-decisions-write-discipline.Tests.ps1` asserts that the **unqualified** "ONLY documented write path" literal is still *present* in each of the three upstream agent bodies, and its failure message instructs an editor to preserve that framing. Appending a qualification leaves it green; deleting one leaves it green too. So a future editor is told by a red test to keep the absolute, and by nothing at all to keep the qualification.

**A second suite is named alongside that one, and it now runs too.** `.github/scripts/Tests/persist-marker-wrapper.Tests.ps1` carries the same presence assertion over a five-file document set, plus the M30 proximity guard. It was **quarantined out of CI** (`class: unclassified`, tracked on [#993](https://github.com/Grimblaz/agent-orchestra/issues/993)) and did not run on pull requests at all, which is why #1011's design and #1032's brief described two suites asserting the absolute while only one executed. [#1035](https://github.com/Grimblaz/agent-orchestra/issues/1035) measured it on Linux and [#1036](https://github.com/Grimblaz/agent-orchestra/issues/1036) promoted it, so both now execute. **The method that found that gap is the part to keep**: re-derive the selection rather than trusting a file's existence — CI picks suites by glob **minus** `.github/scripts/Tests/ci-quarantine.json`, so a suite on disk is still not necessarily a suite that runs.

**If you are rewording a section that carries this qualification, the suite will not stop you. Keep it on purpose.**

## Writing about markers safely

**The hazard**: every marker family in this document is detected by a raw-text scan (`-match`, `[regex]::IsMatch`, `.Contains`) against a comment or PR body — not a semantic parse. Markdown code-span backticks do NOT neutralize these scans: a complete marker literal such as the live delimited form of `judge-rulings pr=5` still matches even inside backticks, because the regex scans raw text and backticks are not stripped before matching. Any prose that quotes a marker literal verbatim — explaining the convention, giving a worked example, or describing what a comment "carries" — is therefore live to the same reader that scans real comments. Two consequences, and **both are still live**: a false positive (a prose mention miscounted as a real block or head), and **a destructive write onto the wrong comment**. A quoted literal can still steer a write: `persist-phase-ledger-core.ps1` selects the plan comment with a *whole-line* match (any line, not just line 1) and then guards every write with `.Contains($ExpectedMarker)` — a marker sitting alone on its own line inside a fenced block or an indented example passes both, and the pointer is then spliced into that comment. Whole-line comment selectors guarded by containment are the surviving destructive transport; assume any new one is too.

**One transport for that destructive consequence is now closed; the other is not.** A quoted literal used to be able to steer a write through `Find-OrUpsertComment`'s `-like` substring matcher, which replaces the selected comment's whole body. Issue #1031 (chunk 1 of #1011) closed that one: `Find-OrUpsertComment` now selects only a comment whose **first line is exactly the marker**, so a quoted mention — mid-line, inside backticks, or alone on its own line inside a fenced block — reaches it no longer. It was not theoretical while it was open: issue #782's approved plan comment quoted `pc-emission-check-report` in prose and was the only match on that issue, so the next emission-check post there would have overwritten the plan. What that fix does **not** reach is the whole-line-selector-plus-`.Contains`-guard transport named in the paragraph above, which still accepts an own-line quotation; nor does it touch the false-positive-counting hazard. Both remain the reason for the discipline below.

**Families affected**: every marker family whose reader does a raw-text scan is affected — this covers every family in the Active Marker Families list above, including `pipeline-metrics`, `cost-pattern-data`, `phase-containment`, `phase-containment-ledger`, `frame-spine`, `frame-slice`, `credit-input`, `engagement-record`, `judge-rulings`, `plan-issue`, `design-phase-complete`, and `experience-owner-complete`. Assume the same hazard applies to any new marker family introduced later unless its reader is proven to do a genuine semantic parse (e.g., a GraphQL comment-id lookup) rather than a raw-text scan.

**The remedy**: use `Format-InertMarkerLabel` (`.github/scripts/phase-containment-emission-check.ps1:148-152`) to render a marker mention in prose. It strips the `<!--`/`-->` HTML-comment delimiters before backtick-wrapping, which genuinely breaks the regex match because the delimiters the pattern anchors on are no longer present in the text at all.

**Worked example**: rendering the live `judge-rulings pr=5` marker for prose reads as `` `judge-rulings pr=5` `` — never with the `<!--`/`-->` delimiters left intact inside the backticks. The same discipline applies to every marker family listed above: write `` `phase-containment-ledger-ref: 123` ``, not the delimited form of that same literal.

This rule was first written for the plan-surface `judge-rulings` block (`skills/plan-authoring/SKILL.md` § Judge-rulings machine block, writer rule 5), which now cross-references this section rather than duplicating it.
